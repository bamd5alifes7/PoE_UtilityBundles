# 技術筆記

## 技術總覽

| 技術 | 用途 | 選擇原因 |
| --- | --- | --- |
| AutoHotkey v2 | 主程式、熱鍵註冊、滑鼠鍵盤模擬、GUI | 這個專案本來就是桌面自動化工具，AHK 直接覆蓋核心需求，不需要額外 runtime。 |
| AHK 內建 GUI | 設定熱鍵、座標、延遲與文字內容 | 設定量很多，用純 ini 維護太痛；內建 GUI 已經夠用，沒有再引入別的 UI 層。 |
| `settings.ini` | 保存使用者熱鍵、座標與行為設定 | 專案是單機腳本，ini 最直白，也方便手動調整。 |
| PixelGetColor / PixelSearch | 自動喝水、撿物、座標探針 | 這些功能本來就建立在遊戲畫面顏色與位置上，直接讀像素比做更重的整合簡單。 |
| 座標 metadata | 共用座標名稱、顯示文字、GUI 綁定與 ini 鍵名 | 原本同一組座標定義散在多個 `switch` 與 GUI 欄位，後續維護成本太高。 |

## AutoHotkey 應用結構

- `PoE_UtilityBundles.ahk`
- `functions_int.ahk`
- `gui.ahk`
- `rw_settings.ahk`

專案維持 AHK 單腳本應用的形態，沒有額外包裝成插件系統或多層架構。這樣做的原因很實際：主要工作仍是熱鍵、滑鼠鍵盤模擬、畫面座標判斷與設定視窗，AHK 內建能力已經覆蓋需求。

目前分檔只依責任切三塊：

- `functions_int.ahk`：實際行為
- `gui.ahk`：設定介面
- `rw_settings.ahk`：ini 讀寫

主程式則保留為薄入口，負責啟動條件、載入設定與註冊熱鍵。這個切法沒有追求高度抽象，但足以把 GUI、設定與自動化行為分開維護。

## 熱鍵與執行模型

熱鍵註冊仍然直接使用 AHK 原生能力，重點在於讓所有快捷鍵都先經過設定值，再由主程式集中註冊。這樣 GUI 變更、設定重載與熱鍵啟停可以共用同一條流程，不需要再維護第二套狀態。

這個應用也沒有另外建立事件佇列或任務排程層。大部分功能維持「熱鍵進來後直接執行對應函式」的模型，原因是這類桌面腳本的除錯成本通常比擴充性更重要；路徑短一點，出錯時比較容易定位。

例外是自動喝水。這一段原本用長時間 `while` 迴圈維持狀態，後來改成 `SetTimer(AutoFlaskTick, 100)`，原因不是功能需求改變，而是 timer 較符合 AHK 的執行模型，也能降低長迴圈卡住其他操作的風險。

## 設定與 `settings.ini`

設定檔目前仍然使用 `settings.ini`。專案沒有改成 JSON 或資料庫，因為它是單機腳本，設定量有限，而且 ini 對 AHK 來說是最直接也最容易人工修復的格式。

這裡實際遇過的問題是編碼。AHK 的 `IniRead` / `IniWrite` 在這個專案內以 UTF-16 較穩定，因此 `rw_settings.ahk` 裡保留了 `EnsureSettingsFileEncoding()`，在讀寫前先校正檔案格式，避免設定值正常但讀寫失敗的情況。

目前設定大致可分成三類：

- 熱鍵
- 行為參數，例如延遲、廣播文字、藥劑列表
- 座標與顏色

這次整理主要集中在第三類。熱鍵與一般文字設定仍維持明確欄位讀寫；座標改成 metadata 驅動，原因是這一類欄位重複度最高，也最容易在 GUI、儲存邏輯與 ini 鍵名之間失同步。

## 座標系統與 GUI

原本同一組座標資訊會分散在幾個地方：

- `SaveCoordinatesTool()` 裡的儲存 `switch`
- `PromptCoordinateSaveOption()` 裡的選單文字
- `GetCoordinateOptionLabel()` 裡的成功提示名稱
- `Coords / Core` 與 `Coords / Stash` 的 GUI 欄位
- `HasUnsavedChanges()` 與 `ApplyGuiValues()` 的欄位同步
- `ReadSettings()` / `SaveSettings()` 的 ini 鍵名

這種寫法的問題不在功能能不能跑，而在維護成本。只要名稱、排序或欄位結構改動，就可能漏改其中一處，像 `Orb of Alchemy` 這類命名就曾在不同位置不一致。

現在的做法是把座標定義收斂到 `functions_int.ahk` 的 `GetCoordinateSlots()`。每個 slot 目前會描述：

- `id`
- `key`
- `label`
- `guiLabel`
- `xVar`
- `yVar`

同一份 metadata 目前會同時提供給：

- save tool 清單文字
- save tool 的儲存對應
- save 成功提示
- GUI 欄位標題與欄位綁定
- unsaved change 比對
- GUI 值回寫
- ini 讀寫鍵名

`Coords / Core` 與 `Coords / Stash` 也改為透過 helper 產生欄位，而不是逐組手刻 `Text + Edit + Text + Edit`。這個改動主要解兩件事：一是欄位名稱變長時容易發生遮擋，二是同類型座標需要維持一致排序與分組時，手刻版面很容易局部修好、整體又失衡。

## Pixel 顏色判斷與自動化功能

這個專案的幾個核心自動化功能都建立在畫面顏色與固定區域上：

- 自動喝水
- 自動撿物
- 游標位置與顏色探針

因此它們有同一組技術限制：

- 解析度或 UI 版面一變，座標就要重抓
- 光線或特效變化會影響顏色判斷
- 這些能力本質上是可調校腳本，不是穩定的遊戲 API 整合

自動喝水目前仍保留重新取樣血量顏色的設定能力，原因是遊戲畫面與濾鏡條件會讓單一固定色值不夠穩定。這不是要把顏色判斷做成通用辨識系統，而是承認桌面腳本的限制，讓使用者可以在畫面條件漂移時自行校正。

## 倉庫與格子座標計算

背包、交易欄與倉庫搬移本質上都在做同一件事：由兩個角點推算整組格子中心，再逐格點擊。

現在共用的核心是 `BuildGridCenters()`。它負責：

- 接收左上與右下
- 根據欄列數計算每格中心
- 回傳可以直接迭代的座標列表

後續的搬移與掃描函式都建在這個基礎上。

這裡沒有再往上包更大的策略系統，因為 `BuildGridCenters()` 已經吸收掉最重複的計算邏輯，剩餘差異多半只是欄列數與延遲設定，繼續抽象化的收益不高。

## 已移除或刻意不保留的東西

專案中有些舊功能已經刪除或移出主要流程：

- 舊的 `SearchItem` 整合
- 傳送卷軸 legacy 流程

原因不是功能絕對無效，而是它們已經沒有穩定的主要呼叫路徑，保留只會增加理解成本與設定噪音。尤其 portal 相關座標在遊戲已有內建替代流程後，繼續保存只會讓設定模型變複雜。

## 目前仍保留的簡化

- `life_color` 還沒有被收進同一套座標 slot metadata，因為它不是 X/Y 對，先保持獨立比較省事。
- `ReadSettings()` / `SaveSettings()` 中，非座標類設定仍然是明確列出，不急著一次 schema 化全部欄位。
- 多數 GUI 位置仍是手動座標，不是完整 layout engine。這個專案的規模下，先把重複欄位收斂，比重寫整個 GUI 值得。

這些簡化都是刻意保留的工程邊界。只有在非座標設定也開始反覆出現同步問題時，再把 metadata 或 schema 擴大，才會有明確維護收益。
